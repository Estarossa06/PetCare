# PetCare data model

## PostgreSQL

PostgreSQL is the shared source of truth and is accessed only by the API. Backend migrations are numbered SQL-schema changes implemented in TypeScript under `api/src/db/migrations/`; they are tracked in `schema_migrations`, applied transactionally, and protected by a PostgreSQL advisory lock. Applied migration source checksums are checked to prevent silently editing migration history.

### Domain tables

| Table | Purpose and key relations |
|---|---|
| `users` | Account identity, unique normalized email, password hash, timestamps and soft deletion. |
| `auth_sessions` | Hashed refresh-token sessions, expiry and revocation. |
| `pets` | User-owned pet profiles. |
| `health_records` | Pet health history; constrained to the same owner as the pet. |
| `health_attachments` | File object key and metadata for a health record; file bytes are not stored in PostgreSQL. |
| `care_tasks` | Recurring or one-time care activities and IANA timezone. |
| `calendar_events` | User-created calendar events only; care, appointments, and medical records remain in their existing domain tables. |
| `calendar_reminders` | Independent, potentially multiple reminders linked to one calendar event, care task, appointment, or health record. |
| `appointments` | Pet appointments and scheduled events. |
| `reminders` | Account data linked optionally to a care task or appointment. |
| `ai_conversations`, `ai_messages` | Pet-scoped conversation history; no provider credentials are stored. |

Syncable domain rows have a UUID primary key, positive integer `version`, `created_at`, `updated_at`, and nullable `deleted_at`. UUIDs generated by a client for offline-created data are sent unchanged to the API. Owner-aware composite foreign keys prevent cross-owner relations, in addition to authorization checks in API services.

### Synchronization support

- `sync_devices`: user-owned device UUID, revocation state and last downloaded cursor.
- `sync_operations`: idempotency receipt keyed by `(user_id, operation_id)`, request hash and stored response. API processing must commit the receipt and domain mutation atomically.
- `sync_changes`: owner-scoped cursor, entity UUID/type/version, change kind, changed fields and operation reference. `(owner_id, cursor)` is the primary key; tombstones are changes too.
- `sync_cursors`: one transactional counter per owner. The counter is updated and its change-feed rows are inserted in the same PostgreSQL transaction.

When an `operation_id` is replayed with the same request hash, the API should return its stored response; reusing that ID with a different hash must be rejected. This behavior belongs to the future sync service and is not implemented by the schema migration alone.

For each mutation transaction, the future sync service reserves a cursor range by atomically incrementing that owner's `sync_cursors.last_cursor` by the number of change rows, then inserts every row in that range before committing. The counter row lock is held until commit, so another transaction for that owner cannot allocate a later cursor until the previous transaction commits or rolls back. Rollback also rolls back the counter update, so it leaves no permanent gap. Pull queries use `WHERE owner_id = $1 AND cursor > $2 ORDER BY cursor`; committed cursors therefore cannot be skipped by a later commit of a lower value.

The reservation statement is:

```sql
INSERT INTO sync_cursors (owner_id, last_cursor)
VALUES ($1, $2)
ON CONFLICT (owner_id) DO UPDATE
SET last_cursor = sync_cursors.last_cursor + EXCLUDED.last_cursor
RETURNING last_cursor;
```

For `$2 = event_count`, the returned value is the end of the reserved range; its first cursor is `returned_value - event_count + 1`. The writer must insert all events in that range and commit them with the domain mutation.

`sync_changes` intentionally does not duplicate full domain payloads. The synchronization service will fetch the current owner-scoped entity when building a pull response, while deleted rows are represented by tombstone metadata. Retention and cursor-expiry policy must be defined before implementing the sync API. Writes that produce feed events must allocate their cursor in the same transaction and a single owner scope; cross-owner mutations are not supported by this cursor protocol.

### Indexes and constraints

The initial migrations define unique account emails, owner/entity composite keys, checks for enumerated types, positive weights/file sizes/versions, valid time ranges, and indexes for owner/pet timelines, upcoming appointments and pending reminders. Foreign keys use `RESTRICT` to prevent accidental physical cascade deletion; application deletes are soft deletes. Operational hard purge is outside this phase.

## SQLite

SQLite is the shared Expo app's local source for reads and writes on Android, iOS and Web. The local migrations are implemented in `mobile/src/db/migrations/`: `0001_initial.ts` creates the initial schema, `0002_health_records.ts` incrementally extends medical history, and `0003_care_routines.ts` adds structured care schedules and execution history. They create corresponding domain tables and indexes plus:

- `sync_queue`: pending local operations, retry state and JSON payload.
- `sync_queue_dependencies`: ordering links enforced within the same account.
- `sync_metadata`: per-account download cursor and local schema version.
- `sync_conflicts`: preserved local/server snapshots pending user or application resolution.
- `scheduled_notifications`: device-only OS notification IDs and scheduled revisions.
- `calendar_scheduled_notifications`: device-only scheduled notification status and OS identifier for calendar reminders.

Local rows use the same canonical lowercase domain UUIDs as PostgreSQL. A local-only row starts at `version = 0`; once accepted by the server, its server version is written locally. `owner_id`/`account_id` isolate local data by authenticated account. SQLite migrations have an independent `_local_migrations` ledger and runner; they do not execute PostgreSQL migration files.

The local database migration runner uses the Expo SQLite async database methods. Native database encryption, Web storage protection and production key management are platform-specific decisions documented in `docs/multiplatform-architecture.md`; the current verification scaffold does not claim that SQLite is encrypted.

### Medical history and attachments

The shared medical-history feature stores pet-scoped events in `health_records`. Migration 0002 adds `clinic_name`, `observations`, validated JSON `details_json`, and `next_event_at` for optional category-specific fields and upcoming doses/applications. UUIDs, owner/pet foreign keys, `version`, timestamps, and `deleted_at` remain part of the existing table. The original migration is not edited.

The original SQLite `record_type` CHECK predates the `examination` category. To preserve already-applied schema history, examinations are represented locally as `record_type = 'observation'` with `record_subtype = 'exam'`; the repository maps that pair to the user-facing `examination` category. Other categories use their existing `record_type`.

`health_attachments` stores UUID metadata and a `storage_key`, never file bytes. The bytes are copied into the app's document directory on native platforms or IndexedDB on Web; Expo DocumentPicker supplies compatible file selection. The sync queue receives separate `health_record` and `health_attachment` operations in the same SQLite transaction as their metadata. A medical-record operation depends on the latest queued operation for its pet; attachment operations depend on their medical-record operation. Logical deletion tombstones the record and its attachment metadata without immediately removing file bytes, preserving pending offline references.

The medical feature uses the same provisional local account row from `sync_metadata` as the pets feature. Its shared write-transaction helper serializes writes across both repositories. No remote sync or PostgreSQL file upload is implemented in this delivery.

### Care routines and executions

Migration 0003 adds the care category, description, observations, structured schedule JSON, IANA timezone, `next_run_at`, and optional `ends_at` fields to `care_tasks`. It creates `care_task_executions` as an independent append-only history of scheduled and actual execution times, with `completed`, `omitted`, and `cancelled` statuses. Both tables carry UUIDs, owner/pet relations, versions, timestamps, and soft-delete fields. Each execution is tied to the same owner and pet as its activity; the outbox operation for an execution depends on the latest queued activity operation.

Daily, weekly and monthly schedules recur at their configured local wall-clock time in the activity timezone. Custom schedules use their stored interval and unit; monthly dates are clamped to the last day of a shorter month and return to the original anchor day in later months. A past-due first occurrence remains visible until recorded. Recording an occurrence preserves its scheduled timestamp and writes the actual timestamp for a completion, then advances the schedule without modifying previous execution rows. One-time schedules have no next occurrence after recording.

`care_execution` is currently a local outbox entity only. The PostgreSQL/API schema and remote synchronization protocol have not yet been extended for execution records; that backend migration and API support are prerequisites for syncing care histories. The local implementation does not connect to Neon or perform remote synchronization.

### Calendar events and reminders

Migration 0004 adds local-only user-authored `calendar_events` and independent `calendar_reminders`. The calendar aggregates care task occurrences/execution history, appointments, and scheduled medical events from their existing tables without copying them into `calendar_events`. `calendar_scheduled_notifications` stores per-device notification identifiers/status separately from reminder domain data. See [calendar-and-reminders.md](./calendar-and-reminders.md) for Expo Go behavior and the PostgreSQL/API work required before any remote synchronization.
